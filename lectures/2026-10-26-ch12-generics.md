## 3. Why generics exist — RTTI and the casts problem (§12.1; pp.179–182 area)

Before Java 5, collections were used **raw**: every element was treated as **`Object`**. You **stored** anything and **retrieved** with an explicit **cast**:

| Step | What went wrong |
|---|---|
| **Store** | `list.add("hello")` and `list.add(42)` compile on a raw list — no type discipline at compile time. |
| **Retrieve** | `(String) list.get(1)` compiles but throws **`ClassCastException` at runtime** when the element is not a `String`. |
| **Debug cost** | Failure happens **far from the bug** — at the cast site, not where the wrong type was inserted. |

**RTTI (Runtime Type Information)** means the JVM **knows the actual class** of an object at runtime (via **`getClass()`**, **`instanceof`**, reflection). Raw collections **erase** element type at the container boundary: the compiler cannot prove casts are safe, so it accepts them and the JVM enforces them **late**.

**Generics** move a large class of those failures to **compile time**: a **`List<String>`** rejects **`add(42)`** and lets you **`get`** without a cast to `String` in normal use.

Paraphrase of the book’s motivation: generics are not “syntax sugar” — they document **intent** in the type signature and let the compiler **reject** inconsistent code before you ship.

**Link to Week 2:** you already used **parameterized types** informally (`List<Order>`, `Optional<T>`, **`Comparator<T>`**). Today names the mechanism: **type parameters** on **classes** and **methods**.

Official background: [Oracle Tutorial — Generics](https://docs.oracle.com/javase/tutorial/java/generics/), [dev.java — Generics](https://dev.java/learn/generics/).

## 4. Generic classes (§12.2; pp.182–188 area)

A **generic class** declares one or more **type parameters** (conventionally **`E`**, **`T`**, **`K`**, **`V`**) that stand in for concrete types when the class is **used**.

Conceptual shape (illustration only — you implement **`Pair`** yourself in **#1**):

```java
public class Box<T> {
    private T value;
    public void set(T value) { this.value = value; }
    public T get() { return value; }
}
```

| Idea | Detail |
|---|---|
| **Type parameter** | **`T`** is a placeholder; **`Box<String>`** and **`Box<Integer>`** are distinct **parameterizations** at compile time. |
| **Instance fields** | Can use **`T`** like a normal type name inside the class body. |
| **Construction** | **`new Box<String>()`** — since Java 7, **diamond** **`new Box<>()`** infers type arguments from context. |
| **Raw type (avoid)** | **`Box` without type args** reintroduces the old cast problem; legacy code may still use it — do not in new code. |

**Multiple type parameters:** a **`Pair<A, B>`** (curriculum **#1**) holds two possibly different types — e.g. **`Pair<String, Integer>`** for a label and a count. Order matters: **`Pair<A,B>`** is not **`Pair<B,A>`**.

**Static members:** static fields and methods **cannot** use the class’s instance type parameters (there is no **`T`** until you have an instance). Static generics need their **own** type parameters on the method (next section).

**Contrast with `record`:** a **`record Pair<A,B>(A first, B second)`** is a concise **immutable data carrier**; a generic **class** can enforce invariants, mutability, and behaviour. For **#1**, the curriculum asks for **your own** generic **`Pair`** — choose class vs record and note trade-offs in **`notes/`** (Week 2 decision guide still applies).

## 5. Generic methods (§12.2 continued; pp.188–192 area)

A **generic method** declares type parameters **on the method itself**, independent of the enclosing class’s parameters.

Illustration only (you write **`max`** in **#1**):

```java
public static <T extends Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;
}
```

| Piece | Role |
|---|---|
| **`<T extends Comparable<T>>`** | Method-level type parameter **`T`**, **bounded** so **`compareTo`** is legal. |
| **Inference** | **`max(3, 7)`** and **`max("a", "z")`** infer **`T`** as **`Integer`** and **`String`** without repeating type args. |
| **Non-generic class** | A plain utility class can still expose **only** generic static methods (like **`Collections.sort`** patterns you will see Thu). |

**Why not overload `max(int, int)`, `max(String, String)`, …?** Duplication explodes; one generic method expresses **“any type that supports ordering”** once.

**Comparable reminder:** **`Comparable<T>`** means **natural order** of **`T`** (`compareTo`). Week 4 Thu goes deeper on **`Comparator`** for **external** ordering; today **`max`** is the hook.

## 6. Bounded type parameters — intro only (§12.3; pp.192–196 area)

A **bound** restricts what types may substitute for **`T`**:

| Form | Meaning (today’s scope) |
|---|---|
| **`T extends SomeType`** | **`T`** must be **`SomeType`** or a **subtype** (upper bound). |
| **`T extends Comparable<T>`** | **`T`** must be comparable to itself — typical for **`max`**. |
| **Multiple bounds** | **`T extends A & B`** — **`T`** must satisfy **all** listed bounds (interfaces/classes combined); rare in **#1**, common in libraries. |

**Upper bound intuition:** “**`T` is at least a **`Number`**” lets you call **`Number`** APIs on **`T`** without casting. Example direction for **#1**’s sum method: accept a **`List`** of **some **`Number`** subtype** — the exact **wildcard** spelling (**`? extends Number`**) is **Tue**; today you should understand **why** you need a bound (sum needs **`doubleValue()`** or similar), not memorize every **`?`** rule yet.

**No lower bounds today:** **`? super T`** (PECS) arrives **Tue** with **wildcards** and **type erasure**.

Book §12.3 bridges **bounds on type parameters** (what you write as **`<T extends X>`**) toward **wildcard bounds** on **uses** of parameterized types (**`List<? extends Number>`**) — read the section for the vocabulary; implement **#1** with bounds you can **justify in `notes/`**.

## 8. Mental model: compile-time checks vs runtime (erasure teaser)

The compiler **checks** generic code, then **erases** most type parameters to **`Object`** or their **first bound** in bytecode (details **Tue**). For **Mon**, hold this picture:

```mermaid
flowchart LR
  A[You write List String] --> B[Compiler type-checks adds and gets]
  B --> C[Bytecode uses Object or bound at erasure]
  C --> D[JVM runs without String on List at runtime]
```

## 12. Common pitfalls (Mon)

1. **Raw types in new code** — **`List list = new ArrayList()`** hides bugs; always parameterize.
2. **Wrong cast after `get`** — symptom of raw or inconsistent generics; fix the **declaration**, not only the cast.
3. **`max` without bound** — **`T`** must **`extends Comparable<T>`** (or pass a **`Comparator`**, Thu topic).
4. **Static field of type `T`** in a generic class — not allowed; instance fields OK.
5. **Assuming generics exist at runtime** — **`List<String>.class`** is illegal; erasure **Tue**.
6. **Jumping to wildcards before bounds** — understand **`<T extends Number>`** on **your method** before **`? extends Number`** on parameters (**Tue**).
